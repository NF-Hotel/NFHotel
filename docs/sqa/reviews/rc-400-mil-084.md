## Findings

- **The first plan missed parts of the standards.** S01 asked whether every well-known principle and standard was in the plan. A second read of RFC 9116 and RFC 8615, line by line, found that the first plan:
    - served the file on both listeners, although a file with a Canonical address is to be trusted only at that address and applies only to the name it is fetched from;
    - left the top-level address `/security.txt` without an answer, where the standard allows a redirect and asks that the name is not left to others;
    - sent no content security policy with the file, which RFC 8615 names as good practice beside `nosniff`;
    - had a check that did not tell a requirement of the standard from a recommendation or from a rule of this project;
    - watched the file every week, but not the addresses the file refers to;
    - left out the signature, the key for encryption and the role address without a record of the reason and of the event that reopens each;
    - had a policy without a word on a report without a name, on the confidentiality of the finder, on the news a finder gets, on a date of publication, and on the findings that are not handled;
    - said nothing about how the team handles a report.

  The amended plan covers each of them (findings 7 to 13, criteria 1, 3 to 6 and 8).
- **What is claimed, and what is not.** The plan claims conformance with RFC 9116 and with section 4 of RFC 8615, and ADR-0048 has to show it requirement by requirement. It claims nothing about ISO/IEC 29147 and ISO/IEC 30111, whose texts were not read; what the policy and the handling of a report contain comes from the OWASP cheat sheet and the NCSC page, which name those standards as their base.
- **Four exceptions are S01's to accept.** No signature and no key for encryption (S01 keeps no OpenPGP key yet; a key held by a workflow would prove nothing), a mailbox that is not a role address of the project (the mailbox S01 named is a personal one), and no promise about legal steps (S01's task forbids a policy that permits testing, and such a promise is commonly read as one). Criterion 1 asks for S01's acceptance of them with ADR-0048. A key or a role address that S01 makes later closes its exception with a change of one line.
- **A policy must not read as a permission.** A text that lists what a finder "may" do can be read as leave to test. The plan asks for one plain sentence that neither the policy nor the file gives a permission, with the section of the standard beside it, and keeps the list of forbidden acts.
- **The headers are easy to lose, and one of them is not this milestone's to decide.** The security headers come from the web application, so the location names its own. The public site sends a Strict-Transport-Security of 30 days from the application, and the HTTPS server of the tailnet sends the value of `NGINX_HSTS`; the location sends the value of the application, so this change does not lengthen the policy of the public name through a side door. Its length stays the open decision of S01 from MIL-066, and criterion 5 compares the header of the file with the one of the front page.
- **One source for the file.** Cloudflare can serve a `security.txt` of its own from its dashboard. The file of this plan is the one in git; the weekly look compares the live body with `main`, so another source shows as a difference.
- **The date is a promise of a person.** A date written by each release would never run out while releases go on, and would say nothing about whether anybody reads the reports. The plan keeps a value in git: the check fails 30 days before it, on every pull request, until one line is changed, and the weekly look opens an issue when no pull request comes. The mailbox S01 named is a school mailbox: the date must not lie after the day it closes, which only S01 knows.
- **No contact is invented.** The first Contact is the private report form of GitHub that `SECURITY.md` already names and that is turned on for the repository; it needs a GitHub account. The second is the mailbox S01 named in chat on 2026-11-17.
- **Only what the texts ask for.** Three things go beyond the task as S01 wrote it, each from a text: the redirect of `/security.txt` (RFC 9116, section 3), the line `Bug-Bounty: False` (the registry of IANA), and the section on the handling of a report (the NCSC page). Left out on purpose: the fields Acknowledgments, Hiring and CSAF (nothing to point to), a probe of the monitoring for the file, a Danish copy of the policy (the repository is in English; Preferred-Languages says that a report in Danish is welcome), and any change of the web application.
- **Nothing in the issues is sensitive.** The tasks name no weakness of the site, so the milestone can be published as soon as it is accepted.
- **Mode.** Planned in supervised mode; autonomous since S01's word of 2026-11-19: the AI commits, opens the pull request and merges it when the checks are green, and approves only the CD run that its own merge starts, as S01 allowed in chat the same day ("du må gerne godkende deploy"; "Automode og deploy").
