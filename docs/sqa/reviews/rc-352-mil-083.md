## Findings

- **The repository installs the runtime with the escapes.** Step 2 of `create-monitoring-lxc.sh` installs Debian's `docker.io`, so a rebuilt LXC, the way back of the wiki page Disaster-Recovery, would bring the escapes back. Task 4 changes the script; without it the fix would last only until the next rebuild.
- **The new runtime can fail in the LXC.** Users reported in November 2025 that the AppArmor rules of the Proxmox node refused the new writes of `runc` to `/proc` in an unprivileged LXC, so containers did not start, until Proxmox VE 9.1.1. The node's version is read in task 2 before task 3, and the snapshot is the way back; a failed start stops the work, it does not lead to a weaker profile for the LXC.
- **The issues are synced after the fix, not before.** The repository is public, and an issue that names three escapes in a host that still has them points an attacker at it. The plan keeps the document, this review and the issues on a local branch until task 3 is done; nothing goes under `src/` or `tests/` (the changes are in `ops/` and `docs/`), so the plan-first gate holds with the accepted document.
- **The floor turns the fix into a control.** The page Container-Escape relies on a person who reads the advisories; the floor stops the deploy of either host on a `runc` below it. It has to compare per line (1.2 from 1.2.8, 1.3 from 1.3.3, later lines as they are), or 1.3.0 to 1.3.2 would pass a plain minimum of 1.2.8.
