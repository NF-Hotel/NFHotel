## Findings

1. **RC-308 overstated a test, and the gate adds the check.** RC-308 said that `test-backup-settings.sh` proves that a backup fails when its list of paths lacks `/etc/nfhotel` or the key of the copy. Its check made `tar` fail, which leaves the guard after the list ("the settings archive would lack …") untested, so the test of #587 did not meet criterion 4. Under task 3, this pull request adds two checks: a copy of the script without the line that adds `/etc/nfhotel`, and one without the line that adds the key, must each fail the backup with that message and leave no settings file. They pass, and they fail against a script without the guard, so they catch its loss. RC-308 records the correction in a new row.
2. **One deploy for two milestones.** The CD run of 42de1fc (42489880568) was cancelled at S01's request, and GitHub cancelled the one of b1abd8e (42491590120) in the queue ([RC-312]), so the CD run 42498483148 of ebbf921 deployed the code of MIL-066, its ZAP rules and the code of MIL-067 at once.
3. **The settings archives before the deploy (task 3).** Finding 3 of MIL-066 leaves `/etc/nfhotel` and the key out only on a host without `ops/deploy/nginx/tls`. On the VM that folder has existed since 2026-10-21 05:35 UTC (its birth time in `stat`), three days before the oldest settings archive on the backup target (2026-10-24 21:43 UTC), so no archive on the target was written in the case of finding 3. The sizes agree: the archives were 41160 bytes up to 2026-10-28 and are 51400 bytes since, the size of the archives of 16:13 and 16:56 UTC, whose logs name 15 paths with `/etc/nfhotel`; the step came after the settings file of the tailnet relay of PostgreSQL was created on the VM on 2026-10-28 at 12:14 UTC. No archive was opened: the age identity that decrypts them is kept by S01, not on the VM, so S01 can confirm one with `age -d` and `tar --list` (action item).
4. **RC-312 corrected.** RC-312 called Proxy Disclosure (40025) "the alert on the name of nginx that the ZAP rules already know". Task 7 removed its `IGNORE` line (#585), so the full scan runs this active rule again, and it warns as a new Medium alert, which does not fail the scan. This pull request corrects the two sentences of RC-312 in a new row; its verdict does not change.
5. **Docker Engine updated without a restart of the containers.** The question to S01 said that the containers would restart briefly. The daemon now runs 29.9.3, so it restarted, but with `live-restore` on no container did. Docker does not promise this for every upgrade, so the step of Host-Hardening still plans for a short restart.
6. **Outside MIL-066: the VM runs a desktop.** While reading how the VM is patched (criterion 8), the gate found that the VM starts `graphical.target`, with the display manager of GNOME, the print service (`cups`, `cups-browsed`), `avahi-daemon`, ModemManager and LibreOffice (20 packages), installed by the task selection of the Debian installer (`task-desktop`) on 2026-09-04; [ADR-0010] does not name them. The firewall drops every inbound packet that its rules do not accept, so the services that listen are not reachable from outside the VM; each is still software that the server does not need and that must be patched, and LibreOffice has security updates waiting. Removing the desktop changes the VM and is not in this milestone; S01 decides (action item).
7. **Outside MIL-066: what the patching does not cover.** The patching installs only the security origin of Debian. Its runs on 2026-11-07 and 2026-11-08 found nothing to install, and the security updates that wait now (LibreOffice, vim and zlib) came with the security archive of 15:51 UTC, so its next run, on 2026-11-09 at 05:23 UTC, installs them. Two packages of other repositories are behind and covered by neither the patching nor the update command of Host-Hardening: the Tailscale client of the VM is 1.102.4 (1.104.5 is out; finding 8 named only the client of CD), and `docker-buildx-plugin` 0.38.1 waits in Docker's repository. An update of Tailscale restarts `tailscaled`, which carries the deploys and the tailnet relay of PostgreSQL, so it waits for S01 (action item).
8. **Nothing prunes the backup target.** The copy never deleted on the target (it has no `--delete`), and since task 1 it cannot. On 2026-11-08 the target holds 425 files, 841 MB, written since 2026-10-21, while the VM keeps its newest 14 daily and 8 weekly backups. Only the backup host can remove old copies; S01 decides a retention there (action item).
