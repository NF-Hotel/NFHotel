## Specific review points

### (a) Architecture

- Dependencies point inward: the Domain entities use `System.ComponentModel.DataAnnotations` and Domain namespaces only. Application references Domain and its own ports (`IClock`, `IUnitOfWork`, `IStaffCallContext`). The architecture tests pass and `StructureTests.cs` was extended.
- The Web layer reaches data only through `IUseCaseRunner<IPriceSuggestionService>`, `IRoomRateService` and `IPricingSettingsService`, which the ApiClient implements over `ApiGateway` (`ApiPriceSuggestionService.cs`, `ApiRoomRateService.cs`, `ApiPricingSettingsService.cs`, registered in `ApiClient/DependencyInjection.cs`). No `DbContext` and no `Microsoft.EntityFrameworkCore` in `NFHotel.Web` or `NFHotel.ApiClient`.
- The Domain has only the allowed folders (criterion 17).
- Observation, not a defect: `RoomListViewModel` (Web) now holds a second runner `IUseCaseRunner<IPriceSuggestionService>` and its `DescribePrice` calls the static formatters of `PriceSuggestionsViewModel`, so one view model reaches into another (F14).
- The ApiClient builds routes with `InvariantCulture` (`$"{ApiRoutes.PriceChanges}/{id}/revert"`) and escapes the size with `Uri.EscapeDataString`.

### (b) Security

- Every action of the four controllers carries `[RequiresPermission(...)]`; every write carries `[EnableRateLimiting(StaffController.WriteLimitPolicy)]` (`PriceChangesController.cs:53`, `PriceSuggestionsController.cs:45`, `PricingSettingsController.cs:45`, `RoomRatesController.cs:46`). `GET /api/room-rates` needs `RoomsView`, all other actions `ManagePrices`. The tests `EveryRoute_*` prove 401 and 403.
- The permission is `Prices.Manage` (`Permissions.cs:50`, from MIL-030, held by the Manager only: `RolePermissions.cs:50`), not `Pricing.Manage` as the milestone text says (F10).
- The approve endpoint recomputes the percentage on the server: `PriceSuggestionApproveRequest` holds only the key and the optional dates; `PriceSuggestionService.ApproveAsync` takes `match.Percentage` from its own computation (`:94`); a key that is not in the current computation gives 404 (`Approve_UnknownKey_Returns404`). Pass. The dates are the only free input; a period wholly in the past is accepted (F12).
- No secrets in logs: the new code has no logger and reads no token. The audit text holds sizes, numbers, dates and user names (`ApprovedDetail`, `RevertedDetail`, `Differences`); `StaffAuditEvent.Create` cuts it to 200 characters and `SetAsync_LargestAuditText_NeverExceeds200Characters` shows the worst case. `ByCallerWithDetail` says the text must not hold a secret; that is a convention, not a check.
- Input validation: the entities are the authority and the services build the candidate first (`PriceChangeService.cs:69-78`, `PricingSettingsService.cs:340-358`); size names match by name so "1" or "7" is refused; ranges and the 366-day limit are in the entities.
- SQL only through EF (`Where`, `FirstOrDefaultAsync`); no `FromSql*` in `src`.
- Razor encodes: no `MarkupString` and no `Html.Raw` in the new pages; the AI text is output as `@explanation`.

### (c) Money

- `decimal` everywhere for prices and percentages; rounding `Math.Round(..., 2, MidpointRounding.AwayFromZero)` in `RoomRate`, `PricingSetting` (`Round`), `PriceChange`, `PriceChangeService.PriceWith` and `PriceSuggestionRule.Build` (and the occupancy with one decimal). Tests: `Suggest_RoundingMidpoint_GoesAwayFromZero`, `Suggest_PriceWithDecimals_RoundsToTwoDecimals`, `GetEffectivePriceAsync_ManyDecimals_RoundsToTwo`, `SetAsync_ThreeDecimals_StoresAndAuditsTwo`.
- Invariant culture in the audit text and the keys: `string.Create(CultureInfo.InvariantCulture, ...)` in `PriceChangeService.Describe`, `ApprovedDetail`, `RevertedDetail` and `PriceSuggestionService.KeyOf`; `Format` in `RoomRateService` and `PricingSettingsService` uses `CultureInfo.InvariantCulture`; the Web reads with `NumberInput.TryParseDecimal` (invariant, no thousands separator, no exponent) and writes with the same culture.
- The only money defect is F1: the percentage is not cut together with the price.

### (d) Concurrency

- `PriceSuggestionService.ApprovalLock` (`static readonly SemaphoreSlim(1, 1)`, `:20`; taken at `:81`, released in `finally` at `:99`) serialises "compute the suggestion, check the overlap, save" for approvals in one process. Proven by `ApproveAsync_TwoAtTheSameMoment_CreateOneChange`.
- Limits: (1) the lock is per process, so two API instances can both pass the overlap check; (2) the database has no guard: no exclusion constraint on size and period, no check that `first_day <= last_day` or `percentage <> 0`, and the index `ix_price_change_size_first_day` is not unique (`PriceChangeConfiguration.cs:29`); (3) `RevertAsync` is outside the lock, which is harmless to the overlap rule (a revert only shortens a change); (4) `IPriceChangeService.ApproveAsync` is public and does not lock itself; today its only caller is `PriceSuggestionService`, but a second caller would bypass the lock; (5) the wait uses the request's token, so a queued approval can be cancelled. The code states the single-instance assumption in a comment (`:17-19`), which is honest. The effective price tolerates two overlapping changes (`EffectiveAsync`: the last approved wins, no throw). See F5.
- No row version on `room_rate`, `pricing_settings` or `price_change`: the last write wins on a rate or the settings. A simultaneous first save of the same size, or of the settings row, hits the unique index; `UnitOfWork.cs:48-75` turns that into `UniqueConstraintViolationException`, which `RoomRateService.SetAsync` and `PricingSettingsService.SetAsync` do not catch (F13).

### (e) `BookingService` and `MarketAnalysisBookingQueries`

- Two-save flow (call at `BookingService.cs:327-340`, `FindPricePerNightAsync` `:352`, `StorePricePerNightAsync` `:382-411`): the price is looked up before the booking is added, the booking is saved by `SaveAndDescribeAsync`, and only then, with the key known, the `BookingMarketDetail` is added and saved in a second `SaveChangesAsync`. The two saves are not one transaction.
- The second save's exception is swallowed (`:404`, `catch (Exception exception) when (exception is not OperationCanceledException)`, then `_marketDetails.Discard(detail)`). Nothing is logged: `NFHotel.Application` has no `ILogger`, and `exception` is not used. The result is a booking that exists without a price and no trace anywhere that the price was lost. The reason in the comment is sound (the booking must stay) and `CreateAsync_SavingTheDetailFails_KeepsTheBookingAndDiscardsTheDetail` proves the behaviour, so swallowing is acceptable as a design; doing it silently is not (F2). A cleaner design gives the detail the `Booking` navigation so that one save writes both and no swallow is needed.
- The remark of `FindPricePerNightAsync` says an error from the lookup is treated as "no price", but only a failed `Result` is; a thrown exception propagates and fails the booking before it is saved (F9).
- The price is fixed at the arrival date for the whole stay, as the milestone says ("on the arrival date", "new bookings only"); `BookingPriceTests.ApproveAsync_AfterTheBooking_LeavesTheStoredPriceAlone` and `ConfirmRescheduleAndCancel_AfterTheBooking_KeepTheStoredPrice` show that a later approval, a reschedule or a cancel does not change it.
- `MarketAnalysisBookingQueries.IsPriceOnly` (`:95`, used at `:66`): a row whose counts are all 0, flag off and texts all null reads as "unknown" for the traits, with the price kept. The heuristic couples two places by an unwritten rule (the zeros that `StorePricePerNightAsync` writes) and it would also hide a real imported row that is all zero and all null (not checked against the seed file). `GetBookingsAsync_BookingMadeByTheHotel_HasNoGuestCountsOrFlags` proves the intended case; no test uses an all-zero imported row. Acceptable as a first edition; an explicit marker would remove the guess (F10).
