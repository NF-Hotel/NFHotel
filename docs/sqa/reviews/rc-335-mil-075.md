## Findings

- **Why the script changes, not only the list.** Taking the key off the web's list alone would make the deploy write the line of `nfhotel-web.env` on the VM into the web's environment. `check-secret-env.sh` would catch it by its name and roll the deploy back, so the plan makes the script leave out the secrets of every service and warn, and the deploy works before S01 or S03 removes the line on the VM.
- **No code of the web needs the key.** The web gets its use cases through the API (`AddApiClient`); the test of criterion 2 proves that it starts without the key before the compose file changes.
- **The order on the VM.** The deploy comes first; then S01 or S03 removes the line in `nfhotel-web.env`, because the AI's writes over SSH to the VM are refused by its safety check. Until then the deploy warns and goes on.
- **A secret file left behind.** The web's old key file would stay in its folder on the VM unless the script deletes it; the deletion of a file that a service no longer lists makes criterion 3 hold after the first deploy.
- **Not independent.** The AI that walked the checklists wrote the plan; the acceptance is S01's decision.
