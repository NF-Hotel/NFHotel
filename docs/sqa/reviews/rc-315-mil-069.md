## Findings

- **The floors follow from the copy.** The copy sends every backup that the target lacks (`rsync --archive --ignore-existing` in `backup-database.sh`), and the VM keeps 14 daily and 8 weekly files (`DAILY_KEEP=14`, `WEEKLY_KEEP=8`). A prune that deleted a file the VM still keeps would see it come back with the next copy. The floors of the newest 14 and 8 files of each kind make that impossible, and criterion 4 checks it.
- **Age, not count.** Every CD run takes a backup before its migrations, so the target got 201 daily dumps in 18 days. A rule by count, as on the VM, would keep only a day or two after a day of many deploys; a rule by the time in the name keeps a known time, however many deploys there are.
- **The key of the VM stays write-only.** The prune runs in its own service on the backup host, without a network. The ssh service and `rrsync -wo -no-del -no-overwrite` do not change, and criterion 2 keeps their tests.
- **The plan matches the code of `main` at e2dadb6.** `backup-database.sh` names the four kinds of file (`nfhotel-daily-*.dump.age`, `nfhotel-weekly-*.dump.age`, `nfhotel-settings-daily-*.tar.age` and `nfhotel-settings-weekly-*.tar.age`); `ops/deploy/backup-target` holds the `Dockerfile` with the user `nfhotel-backup` and the folder `/backups`, `backup-target.env.example`, `docker-compose.yml` and `entrypoint.sh`.
- **The redeploy needs S01.** Task 5 rebuilds the target on the backup host only after S01 approves it in chat, as on 2026-11-08.
- **An abbreviation was changed before this record.** AI is spelled out in task 5 (criterion 10).
- **The acceptance covers the language and the terms.** As for MIL-067 ([RC-309]), criteria 3, 5 and 9 rest on the acceptance of S01, who can challenge them in the summary of the run.
