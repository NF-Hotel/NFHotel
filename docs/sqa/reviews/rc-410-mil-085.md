## Findings

- **A UUID names a booking; it is not the key to it.** The standard for UUIDs says that one must not be used as a capability, and ASVS says that a UUID has too few random bits for a secret. The plan follows both: the reference takes the place of the counting number, and the email with the limit on wrong tries stays the lock (decision 2).
- **A reference of 36 characters is long.** S01 asked for it. Nobody has to type it when it is copied from the receipt, and a guest on the phone with the hotel is found by name and dates. A shorter random code is among the alternatives that ADR-0049 has to weigh.
- **Old numbers stop on the day of the deploy.** That is the point of decision 5. A guest who holds an old number reaches the hotel, and staff find the booking by guest and dates; task 6 looks on the live site at what the bookings in production are.
- **The migration must be safe to roll back.** Criterion 2 asks for the smoke test of the release before this one against the migrated database, because the deploy rolls back by itself when its smoke test fails.
- **The reference in the address of the page that finds a booking** ends up in the history of the browser. That is accepted, because the reference opens nothing alone.
- **Mode.** Autonomous: the AI builds, reviews as stand-in, opens the pull request and merges when the checks are green; S01 approves each run of continuous deployment.
