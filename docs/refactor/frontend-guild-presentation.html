01 · The legacy

We inherited a WPF project from another group

1,093
lines of XAML in one view file
823
lines in one ViewModel
0
async methods in the entire data access
126
business rules extracted

The assignment said "port to Blazor". But WPF bindings, converters and code-behind have no counterparts in Razor. There was nothing to port — the UI had to be written from scratch.

What we took with us: Map the rules before you touch the markup. If you do not know what the old screen did, you recreate its mistakes.
01 · The legacy

Four business rules lived in a colour converter

The calendar drew bookings as bars. The width was (EndDate − StartDate).Days — that is, the number of nights, not days. A bar started in the middle of the arrival day, because the room is only occupied from noon.

  • None of those rules were in the domain. They existed only as numbers in a converter, between 40 lines of comments where someone was thinking out loud.
  • We found them because we had to rewrite the UI. Had we "just ported", they would have vanished silently.
What we took with us: Frontend code is a hiding place for domain knowledge. A converter, a *.css class or a disabled attribute can be the only documentation of a rule.
02 · One rule

.razor is markup. Full stop.

All logic lives in a ViewModel class, injected via the constructor. Not code-behind, not @code blocks with business rules.

The test we use

Can a console app call the same use case and get every rule enforced?

If the answer is yes, an API can too — and the mobile app inherits the rules for free.

What it gave us

When the customer site was built later, it required zero changes in the business logic. A whole new audience, the same services.

What we took with us: The rule is not an architecture fetish. It is the reason the next layer can be built without touching the previous one.
03 · The system before the screens

We agreed on 63 CSS classes before the first line of markup

forestbrasssandlineink

A written spec with colour tokens, typography and an exhaustive list of class names. No Bootstrap, no external fonts — the app must work offline.

  • The spec was a contract, not inspiration. Three areas were built in parallel by different people against the same class list.
  • Nobody invented their own classes. This was checked mechanically: every class in markup had to exist in the CSS.
What we took with us: A design system is cheapest to write before the screens and most expensive afterwards. Write the class list down — then several people can work at once without drifting apart.
04 · The boundary

The UI must not guess what is allowed

The temptation
@if (booking.Status == Pending
    || booking.Status == Confirmed)
{
    <button>Cancel</button>
}

// Now the state machine exists
// in two places. They will drift
// apart.
What we do
@if (booking.Actions.CanCancel)
{
    <button>Cancel</button>
}

// Actions comes from the domain.
// Same source as the guard in
// the Cancel method itself.

We lacked this for rooms and got 11 buttons that were always visible — and a service that objected afterwards. It was fixed by letting the domain answer, not by copying the rules up into markup.

What we took with us: If a button can give an error when you press it, the UI and the domain disagree. Let the domain decide what is drawn.
04 · The boundary

Error codes down, Danish text up

The domain returns
"guest.email_invalid"

A code. No choice of language, no wording, no assumption about who reads it.

The UI translates
"Enter a valid email"

One place in the frontend with all the Danish texts. If the system needs to be in English, it is one file.

The old system had English user texts inside the models' Validate() — and swallowed check-in errors in Debug.WriteLine, so the user never saw them.

What we took with us: Language is presentation. If the text lives in the domain, you have tied the business logic to one language and one audience.
05 · How we used AI

The spec was the contract between parallel agents

  • One agent per area, owning specific folders. Foundation and design system, customer flow, admin. They never touched each other's files.
  • The contract was written in advance — the class list, the component names, the route structure. Without it, three parallel agents would have invented three design systems.
  • Verification was independent of whoever built it. An agent that had to draw two design documents in the same diagram found that they had written directly opposite rules for when a room is occupied.

Neither of the two would have found that error in its own document. It became visible because someone had to use them together.

What we took with us: Parallelising requires a contract, not just a split. And never let whoever built something be the only one who checks it.
05 · How we used AI

What we would do differently

  • Write the design system even earlier. We first built three lists in Bootstrap and discarded them. That was wasted work, not research.
  • Define Actions for all entities from the start. Bookings had it; rooms did not. The difference was visible directly in the UI quality.
  • Put accessibility in the spec, not afterwards. Focus markers and labels were fixed at the end — they should have been in the class list.
  • Write the test plan at the same time as the screens. We wrote it last and only then discovered that the create forms were missing.
What we took with us: The mistakes that cost the most were all ordering mistakes — not technical ones.
Summary

Four things you can take to your own projects

  • Read the old frontend as documentation. Rules hide in converters, disabled attributes and CSS.
  • Write the class list down before markup. It is what makes parallel work possible.
  • Let the domain answer what is allowed. Not an if in your Razor.
  • Keep language out of the business logic. Codes down, text up.
The real frontend work was not making the screens look right. It was finding out what they should show — and where that knowledge belonged.
